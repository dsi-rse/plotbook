# plotbook — motivations and design rationale

This document explains *why* plotbook is shaped the way it is. The companion
`PLAN.md` states *what* to build; when the plan underdetermines a choice, resolve it
in the spirit of this document. The recurring themes are: the human controls the
narrative while the machine detail is subordinated; artifacts must remain plain files
that need no running software to inspect; anything irreversible happens only on an
explicit human action, through fixed code rather than model-composed commands; and
the tool must never be annoying.

## The problem: what notebooks got right, and where they fail now

Before coding agents, exploratory data analysis lived in Jupyter (and before that,
Mathematica) because a long notebook acts as a scientific notebook: a chronological
story of what was tried, what worked, what was abandoned, and what was settled on.
That chronological-record property is the thing worth preserving. But notebooks have
real costs. You need a running server merely to *look at* one, which makes casual
inspection of past work annoying. Hidden kernel state makes results depend on
execution order. The file format is hostile to git. And in the agent era a new
problem dominates: when Claude Code does the typing, its explanations of what it
produced are far too detailed to serve as the narrative of a scientific exploration.
The details must exist somewhere, but not at the level where a human scans the log
looking for a previous result.

plotbook splits the notebook's roles apart. The chronological record becomes git
history, a long-lived GitHub PR comment thread, and saved conversation transcripts.
The live view becomes a small local web page. The artifacts become ordinary files —
SVG plots and short Python scripts — that any file manager, browser, or editor can
open with nothing running. Each role is served by the medium best suited to it, and
no role holds the others hostage.

## The editorial principle

The central struggle of agent-assisted analysis is controlling complexity, and the
core design rule follows from it: **the publication step is never automatic, and the
human's words are never machine-edited.** The PR comment is the narrative level — the
thing a collaborator (or the author, months later) scans to follow the scientific
story. The human writes it. Claude's commentary is valuable but belongs one level
down, collapsed inside a `<details>` block titled "🤖 Extra details 🤖", where it can
be expanded when the reader wants depth and ignored when they don't.

The addendum is generated when the drafting view opens, not when Publish is pressed,
and it lands in an editable pane beside the human's draft. This serves the editorial
principle twice over: the human sees the machine's account of the work *while*
writing their own, free to steal phrases from it, correct it, or delete it; and what
gets published is exactly what is in the pane — the model proposes, the human
disposes. A pleasant side effect is that the publish pipeline itself contains no
model call and is therefore deterministic and fast.

Everything that *is* automatic — per-turn commits, transcript syncing — is local and
reversible. Everything that leaves the machine — pushes, comments — happens only when
the human clicks the button.

## Why WET scripts in plain directories

Every plot is produced by a self-contained script: Write Every Time, not Don't Repeat
Yourself. This is a deliberate inversion of software-engineering instinct, justified
by what exploration actually needs. A plot's script is its complete, frozen recipe;
there is no hidden state and no execution-order dependence; any plot can be
regenerated by running one file; and scripts can be referred to by name in
conversation ("make a plot like primary0102, but with such-and-such an additional
constraint") because each name denotes exactly one immutable thing. Scripts are never
edited once superseded — corrections get new numbers — so the sequence of files *is*
the chronological record, and the numbering makes the whole system self-indexing:
the same `primary0117` string appears in filenames, commit subjects, transcripts, and
PR comments, so provenance questions reduce to grep.

Outputs are SVG because the author edits figures in Inkscape afterward, which also
drives a subtle convention: matplotlib's `svg.fonttype = "none"` keeps text as text
elements rather than outlined paths. The author explicitly values later editability
over pixel-exact font rendering; if a font is missing on some machine, substitution
is the acceptable failure mode, so the default is a widely available bundled font
rather than any embedding scheme (which Inkscape handles poorly anyway).

The directory layout keeps the analysis root down to three entries — `plots/`,
`scripts/`, `.plotbook/` — so that a user-added README or similar is never lost in a
long listing. `plots/` contains only outputs, which makes it exactly the directory a
user browses with Finder's thumbnails when the viewer isn't running; `scripts/`
holds the recipes; `.plotbook/` holds everything the user rarely opens, including the
committed transcripts and the publish manifest, with its own internal `.gitignore` so
the enclosing repository's conventions are never touched. plotbook deliberately owns
nothing above its directory: the user creates the branch, the PR, the repo-level
`.gitignore` and `requirements.txt`. These analyses drop into larger projects the way
`notebooks/` directories do today, and the tool must be a polite guest.

## Threads

A thread is one Claude Code session's line of work, named by the user with a short
mnemonic word. The common case is a single `primary` thread with an occasional
`tangent` for a side question, each thread being a separate Claude Code instance with
its own viewer tab. One live session per thread, enforced by a claim file, gives each
numbered sequence a single writer — which makes number allocation trivial and gives
each viewer tab a well-defined chronological sequence to walk. Concurrency across
threads is handled structurally rather than by care: sessions stage only the files
they themselves produced, commits are serialized by a lock, and the only genuinely
shared namespace (shared-library numbering) is claimed atomically.

## The shared library: an append-only tree of deltas

Pure WET would have every script re-write the same helper functions, inviting
transcription drift. A conventional mutable library breaks the opposite way: changing
an interface silently breaks the reproducibility of every earlier script. The
resolution is an append-only *tree* of delta files. Each `shared_NNNN.py` re-defines
only what changed relative to its parent; nothing is ever edited; and each plot
script pins one leaf of the tree.

The tree shape, rather than a linear sequence, exactly mirrors exploration itself. An
analyst goes down a tangent, decides it was a bad idea, and wants to resume from an
earlier set of procedures and assumptions — which is precisely "create a new delta
whose parent is the pre-tangent node." It also makes concurrent threads safe: two
sessions allocate different numbers with different parents, so lineages can never
interleave into each other.

The mechanism is deliberately the dumbest possible working Python. A delta's first
line is `exec(open("scripts/shared_0007.py").read())` — simultaneously the code that
loads its ancestry and the machine-readable tree edge. Because `exec` without a
namespace argument runs in the enclosing namespace, execing a leaf recursively merges
all ancestors, root first, into the plot script's own globals; later definitions
replace earlier ones *for intra-library callers too*, because every function shares
those globals. That late-binding property is the reason exec beats `from x import *`
(star-imports only rebind names in the importer, so a helper calling an overridden
helper would silently use the stale version). Order confusion is impossible by
construction: the model writes a single leaf name per script, and the load order is
derived by following parent lines, never recalled from memory.

Two conventions make this robust. Scripts always run from the analysis root
(`python scripts/primary0117-foo.py`), because the exec paths and the `plots/` output
path are root-relative; the root delta begins with a guard that fails immediately and
legibly when run from the wrong place. And the parent line has exactly one canonical
form, on the first line, one per delta, so tools can parse the tree with a regex and
a guard hook can enforce immutability and form. Reproducibility at HEAD follows: old
scripts keep working because nothing they pin ever changes, and git time-travel
becomes a rare luxury (handled, when needed, by `git worktree` so the working tree
and its uncommitted files are never disturbed) rather than a required ritual.

## Conversations as artifacts

The transcripts saved into git are not agent memory and are not meant to be resumed.
They are evidence — unedited primary sources to be mined later for questions like
"what was I asking for when I requested this plot?" and "under what assumptions did
we choose that?" Because they are committed in the same per-turn commits as the
scripts and plots, the conversation that produced a result is git-bound to the
result.

The filtering philosophy: keep both sides of the dialogue verbatim; reduce tool
activity to one-line anchors ("wrote primary0117-….py", "ran python scripts/…")
because the file contents are already committed and would be double-counted; drop
model reasoning blocks entirely, since they are unsearchable, overly detailed, and
were never shown to the human. One filtered format is the single source of truth — no
raw backups in git — a deliberate trade of a small loss window (the transcript format
is internal to Claude Code and changes between releases) against bloat and
duplication. The compensating requirement is that the filter must fail *loudly* the
moment it meets content it doesn't recognize: a visible hook error plus a marker file
in the analysis root, so a format change costs hours of transcript rather than weeks,
while the raw file still sits in Claude Code's own storage for manual recovery.

## Git choreography

Commits happen automatically at the end of every conversational turn; pushes and
comments happen only on explicit human action. This split gives fine-grained history
with meaningful messages — the subject line is Claude's one-line summary of what the
user asked for that turn, in the user's own register ("move legend to upper right"),
prefixed with the artifact range — without ever generating GitHub notification noise
or publishing anything prematurely. The user may push manually at any time purely as
backup; doing so must not affect what the next comment considers "new", which is why
the new-since-last-comment boundary derives from the publish manifest and never from
push state.

A structural decision sits underneath all of this: **the model never runs git or gh
directly.** All git mutation lives in fixed, reviewed scripts invoked by hooks and by
the publish pipeline. This is partly safety (nothing is committed or published except
through one deterministic ritual) and partly compatibility: Claude Code permission
deny-rules merge across all settings scopes and cannot be overridden by any allow
rule, so a user who globally denies `git *` — a sensible precaution against agents
committing to important repos — can still use plotbook, because its scripts never
match that rule. Commit scoping is equally structural: a session stages only the
scripts it wrote (known from the tool-use journal) and the outputs bearing its thread
prefix (outputs are created by Bash-run Python, invisible to write journals), by
explicit pathspec, confined to the analysis directory. Never `git add -A`.

Published images are linked, never uploaded, because GitHub offers no comment-
attachment API — and linking turns out to be strictly better: the artifact's filename
is visible in every URL, which solves the "which file was this plot?" problem that
plagued the manual copy-paste workflow this tool replaces. Links are pinned to the
exact commit SHA at publish time, and GitHub retains PR-branch commits via hidden
pull refs even after branch deletion or squash merge, so old comments keep rendering
indefinitely. SVG is served by GitHub's raw host with a non-image content type, so
comments embed a publish-time PNG preview that hyperlinks to the SVG blob at the same
SHA — the preview for reading, the SVG for taking.

## The viewer's ergonomic goals

The viewer exists to replace two rituals from the earlier workflow: closing browser
tabs to manage clutter (each new plot used to open a tab) and hunting through Finder
for old plots. Its contract: one tab per thread, forever. The newest output appears
large on a stage the moment it is written; previous/next controls walk the numbered
sequence; a chronological thumbnail strip reaches deeper history; and a visible
divider marks the last published artifact so "what's new since my last comment" is
always legible. One behavioral rule matters more than any layout choice: a newly
created plot takes the stage only if the user is already viewing the latest —
live-updating must never yank someone out of browsing history. Non-plot outputs
(GeoJSON and the like) appear as cards that can be downloaded or dragged into other
tools (e.g. geojson.io).

The drafting view is a simulated GitHub comment box, and its preview must be
trustworthy: it uses GitHub's own markdown-rendering API for the HTML, with MathJax
(GitHub's math engine — not KaTeX, whose delimiter handling differs) and mermaid.js
applied client-side the way github.com does. Images enter the draft by clicking
thumbnails, which insert an `<img>` at the cursor, because the author writes prose
*between* images, explaining each one — selection and composition are one gesture,
not a checkbox list plus a separate text field.

The viewer is also the place where the anti-annoyance principle bites hardest. It is
one Python file with inline dependency metadata, started idempotently and lazily,
bound to localhost (reachable from a cluster through a plain SSH tunnel, which is how
the remote case is served without any extra machinery). And it is *optional*: because
artifacts are plain files, everything can be browsed with a file manager when no
server is running. The founding grievance here is having to start `jupyter lab` just
to look at a notebook; plotbook must never reproduce it.

## Prior art, and why it was not adopted

The adjacent tools were evaluated and rejected for specific reasons worth preserving
so they are not re-proposed. marimo and marimo pair come closest in spirit, but the
author dislikes the interface and the reactive execution model, and marimo notebooks
cannot be browsed without re-running them — failing the degradation invariant.
Datalayer's jupyter-mcp-server drives a live kernel from Claude Code but proved
unreliable in basic operations (restart-and-run-all executing out of order);
ipython-mcp is too incomplete. claude-code-sciplot renders plots in a terminal side
pane but requires Kitty-graphics terminal emulators, and the author switches between
macOS and Linux using each platform's default terminal. Nothing packaged combines the
three things plotbook is actually about: a WET, thread-numbered file substrate; a
human-curated PR narrative with machine detail folded away; and conversations
preserved in git as minable artifacts. The editorial layer is the novel part.

## What is deliberately out of scope

The known Achilles heel versus Jupyter is that one-off scripts re-load data from disk
on every run. That is left to a *future, separate* cache-server project by explicit
decision: analyses are one-time explorations, so analyses performed before such a
server exists simply never use it, and the question of how scripts source data lives
at a different level of abstraction than notebook management. Crucially, plotbook
places **no constraints on how scripts acquire data** — exploratory analysis is
idiosyncratic, and a mandated loading interface would narrow the tool's usefulness to
protect a feature that doesn't exist yet. Likewise out of scope: Slurm submission
conventions (the viewer already works over SSH tunnels), generating the addendum from
a live session's full context (a possible later refinement of the headless
generation), GitLab, multi-user analyses, and any automation of branch or PR
creation.

## The name

`plotbook`: a book of plots, in the lineage of the author's earlier `histbook`. It is
functionally a ledger — append-only entries, committed as they happen — but "book" is
shorter to type in `/plotbook:start` and `/plotbook:push`, and the PR thread it
produces reads, when it works, like what it replaces: a scientist's notebook.
